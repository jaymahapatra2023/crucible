Architecture record

How Crucible decides

Crucible evaluates hackathon submissions against a challenge — for completeness, innovation, and the organisation's own principles, standards, security and risk posture. This is the whole pipeline, stage by stage: what each step does, which steps a model touches, and the machinery that exists so that a model's confident sentence never becomes a team's elimination on its own.

00Premise

A system built to be argued with

Crucible's design starts from an uncomfortable fact: it is going to eliminate teams, and some of those teams will disagree. Every structural decision in it follows from wanting that argument to be winnable on the merits — by either side.

That produces three rules which recur at every layer:

  • Nothing is scored without a citation. Every score and every finding carries a file path and a line range drawn from a persisted scan, so a disputed judgement can be checked rather than debated.
  • What could not be measured is excluded, never zeroed. A criterion nobody could assess is recorded as unassessed and dropped from the denominator. Scoring it zero would mark a team down for a gap in our reading, invisibly.
  • The model never has the last word. It cannot pick its own evidence, its output is rejected unless it satisfies a schema, it runs twice, and a human decides anything near the cut line.

02Setup

Standing up a challenge

A challenge holds the brief teams answer and the rubric they are judged by. The order below is enforced, not merely suggested: rubric generation is unavailable until at least one document's text has been extracted, because criteria cite passages of the brief by location and there is nothing to cite until the text exists.

2.1

Create and upload

Person

A challenge starts as DRAFT. The organiser uploads a brief and any supporting material — four kinds are recognised: BRIEF, SUPPORTING, RULES, DATA_SAMPLE. Uploads are capped at 25 MiB and streamed rather than buffered.

2.2

Extract the text

Deterministic

Extraction status is tracked per document, not as one summary: PENDING, EXTRACTED, FAILED, UNSUPPORTED. That distinction matters — a scanned PDF with no text layer produces no criteria, and an organiser who sees only an aggregate would generate a rubric from whichever documents happened to work, without being told which those were.

2.3

Draft the criteria

Model

Four registered calls do this work. rubrics.criteria_generate drafts criteria from the extracted brief — the only call in the system with a non-zero temperature (0.20), because drafting is the one task where a little variety helps. Then rubrics.quality_gate checks whether each criterion can actually be scored from a repository, and rubrics.criteria_review and rubrics.criteria_judge run on Opus for a second reading.

The rule the gate enforces

A rejected criterion is regenerated once, then surfaced as NEEDS_REWRITE — never silently dropped. Dropping it would quietly reshape the rubric the committee thinks it is reviewing.

2.4

Set the weights

Person

Weighting happens at two levels, and both are the committee's to decide.

LevelWhat it controlsMust total
Dimension weights How much each of the five dimensions counts toward the composite 1.00
Criterion weights Relative importance within one dimension 1.00 per dimension

Weights that do not total 1.00 block the save and say so. Nothing is normalised silently. A committee setting weights is deciding relative importance; quietly rescaling their input would mean the rubric does not say what they think it says. A dimension weighted zero is labelled not scored at all — which is different from being assessed and scoring badly, and the ranking will not mention it.

2.5

Approve, freeze, publish

Person

Freezing is enforced by a database trigger, not by a service check — a frozen rubric refuses criterion writes at the storage layer. Publishing makes it readable without an account, because teams are entitled to know the standard before they are judged by it. No submission is accepted until a published rubric exists.

A frozen rubric cannot be edited. It can be superseded: a new version carries the source's criteria and dimension weights forward, ready to change. The quality gate's verdict is deliberately not copied — it judged the old wording, and inheriting it would either excuse a fresh problem or condemn a fixed one.

03Intake

Teams and intake

Worth knowing up front

There is no team entity. A team is a name on a submission — team_name, unique per challenge among current submissions. There is no roster, no registration step, and no assignment of teams to challenges. A team joins a challenge by submitting to it. This is a deliberate simplification for a single evening event, and it has real consequences that are catalogued in the companion gap register.

How a team is admitted

Teams have no Crucible account by design — issuing fifty accounts for one evening is all risk and no benefit. A team proves itself with a scoped, revocable submission token instead.

  • The organiser issues one token per team. Only its SHA-256 is stored; the plaintext exists exactly once, in the response that created it.
  • Revocation is checked on every call with no caching, so it takes effect immediately.
  • A token that has never been used is flagged — before a deadline that usually means it never reached the team, and afterwards nothing can be done about it.

How a submission is made

Through a public page. The team gives their name, a contact email, the challenge, the repository URL, and — crucially — how the project builds: either a Dockerfile path or a build-and-start command. That single field is the difference between a probe reporting RUNS and one reporting BUILD_FAILED.

An organiser can also submit on a team's behalf. Either way the same preconditions hold: intake must be open, self-service must be enabled, a published rubric must exist, and the repository host must be on the allow-list (github.com, gitlab.com).

The commit lock

On submission the repository is validated and its current commit recorded. That exact commit is what gets evaluated. Later pushes do not change it — a team wanting a later commit judged must submit again, which supersedes their previous entry with a version bump rather than overwriting it.

The window

Intake reports one of five states: NO_WINDOW, NOT_YET_OPEN, OPEN, CLOSED, LOCKED. Closing is a date and is reversible. Locking is permanent — no further entry, correction or resubmission is accepted afterwards, including from a team whose repository turned out to be private. That irreversibility is the point of it, which is why the two are separate actions.

04Evidence

Scan

Deterministic — no model participates

The repository is cloned at the locked commit and read under an explicit file budget. Nothing downstream ever clones: scoring and discovery both read the persisted scan, because a step that could fetch code on its own would make the evaluated commit, the cost and the timing unpredictable.

What a scan records

  • Source files with paths and contents, up to the budget
  • Metrics: total and code lines, languages, longest files, test/CI/Dockerfile/README presence, dependency count
  • Repository markers read straight from the filesystem, independent of the file budget — so "has tests" stays true even when the budget stopped short of reading them
  • filesAnalysed, filesTotal and budgetTruncated, so "we looked everywhere" is a checkable claim rather than an assertion
  • Provenance: commit-history analysis producing flags, never exclusions — a high single-commit share or work outside the event window is surfaced for a person to judge, not acted on automatically
05Evidence

Probe — yes, it really runs the app

Deterministic — no model participates

This is the answer to "are we able to run the app?": yes. Each submission is built and started inside a container, and the Runs dimension is derived from what actually happened. No model participates in that dimension at all — it is the one objective score in the rubric.

Containment

The probe executes untrusted code, so the sandbox is the highest-risk surface in the system and is tested with deliberately hostile fixtures — a fork bomb, a memory bomb, and a process that attempts network egress.

06Description

Discovery

Model Manual trigger only Off by default

Scoring says how well a submission did. Discovery says what it is: its API surface, its data model, what it can do, what it talks to, what it is built on, and what a security reviewer would want to look at.

How it is run

Manually, per submission, and only that. It is not part of the batch run — the batch stages are scan, probe and score. It is not triggered as a side effect of scanning or scoring. It is gated behind a feature flag that ships false.

The reasoning is cost: roughly seven model calls per submission, describing a submission rather than scoring one. A step that fired automatically would make spend and timing unpredictable across a cohort. The trade-off this creates for a fifty-team event is a real one and is recorded in the gap register.

How it feeds the evaluation

Discovery is the evidence base the evaluation reads from, not a parallel description beside it. The principles and standards evaluators receive a digest of what was found alongside the source excerpts they already get — so a principle about layering is assessed by someone who has been told where the layers are. Two guards hold that honest, and both are enforced in code rather than asked for in a prompt:

  • Additional, never instead. The digest is appended to a context that already contains real source. An evaluator scoring from the digest alone would be grading a summary of the work.
  • A concern that could not be extracted is passed as NOT DETERMINED, never as "none found" — with an explicit instruction not to read it as an absence. If the integrations extractor failed, an evaluator must not conclude the team integrates with nothing and mark them for it.

A submission with no discovery produces an explicit sentence saying none was run and that this is not a deficiency in the submission — not a blank section, which would read as "nothing found".

07Judgement

Scoring

Model Evidence selection deterministic

Each criterion is scored from real source with real line numbers, selected for that criterion. This is the pivot the whole design turns on: an evaluator that received a tech-stack list and a summary blob would be a second-order pass over a description of the work rather than the work.

How evidence is chosen

The model does not choose its own evidence

Selection is deterministic and model-free. Terms are extracted from the criterion's evidence specification — what a reader should be able to point at — and files are ranked by how many distinct terms they mention, with a path that names the concept scoring strongly, tests discounted to 0.7 and documentation to 0.5. A model choosing its own evidence could choose evidence that supports the score it already prefers, and would make two runs incomparable.

What comes back, and what happens when it doesn't

NOT_APPLICABLE earns its place: a dependency-pinning standard has nothing to say about a repository with no manifest, and reaching for NON_COMPLIANT there would mark a team down for the shape of their problem rather than their work.

Every cohort is scored twice

Two independent runs, then compared — not averaged. Averaging would hide exactly the thing worth knowing. Two flags come out of the comparison: straddles_cut (the runs disagree about whether this submission is in or out) and exceeds_threshold (the composites differ by more than 10 points, wherever the submission sits).

08Arithmetic

Aggregate and rank

Deterministic — pure functions, unit-tested

From here to the ranked field there is no model at all. Criterion scores roll into dimension scores with unscoreable items excluded from the denominator; challenge fidelity is normalised within its own challenge cohort; the five dimensions combine by the committee's weights; and the field is ranked globally.

Why fidelity is normalised within cohort

A single global ranking is only valid if "challenge fidelity" means the same thing on every track. Two challenges of different difficulty produce different raw distributions, so fidelity is converted to a percentile standing within its own cohort before entering the composite. The raw score is always preserved for appeals.

MethodWhen
PERCENTILEThe normal case. Ties count as half, so tied submissions stay equal
ABSOLUTE_FALLBACKThe cohort is too small for a percentile to mean anything
DEGENERATE_UNIFORMEvery score is identical — the transform cannot distinguish, and says so rather than inventing an order

The advisory guard

Originality is advisory and carries the lowest weight, and it is structurally prevented from being the sole reason a submission falls below the cut: the cohort is re-ranked with the dimension removed, and any submission whose outcome changes is reported. An advisory signal that could eliminate on its own is not advisory.

09Judgement

Review and decide

Person

The ranked field is presented with the cut band visually distinct, every caveat stated in plain language rather than as a code, and each team's page carrying the evidence behind every number: the criterion scores with their rationale and cited excerpts, the probe result, the provenance observations, and the disagreements between the two runs.

Two constraints enforced by the database, not the UI

  • A caveat cannot be dismissed without a reason. A CHECK constraint ties the dismissal to its justification, so the two cannot come apart.
  • A decision cannot be recorded without a reason. Same shape, same reasoning: the record has to answer "why" three months later.

Finalising the shortlist locks it. And any team's appeal packet can be produced in one action: a self-contained document carrying the rubric text they were judged against, every score with its excerpts, the probe outcome, the flags, the decisions and the audit trail — readable without system access, because an appeal answered with a database query is not an answer.

10Fitness

The calibration gate

Before the system is allowed to eliminate anyone, it has to be shown fit to. That is what the gate is for, and it is designed so that an uncalibrated system is not used by default.

  1. A golden set of at least eight repositories spanning clearly strong, middling and clearly weak — including the edge cases that break naive scorers: scaffold-only, excellent code solving the wrong problem, fails to build, very large.
  2. Hand-ranked independently by at least two people, before any machine scoring.
  3. A calibration report: rank correlation, every material disagreement with its evidence, run-to-run variance, and which dimensions disagree most with human judgement.
  4. Gate criteria written down before the report is produced. Otherwise the criteria become a description of whatever the report happened to say.
  5. The decision recorded with rationale and actor.
If the gate fails

The documented fallback is fully human judging. The system may then be used for evidence gathering only — not for ranking. The ranking endpoints refuse and quote the fallback plan.

11Boundaries

What is deterministic, and what is not

A fair summary of the architecture: the model is asked to read and to judge; it is never asked to select, to count, or to compute. Everything that decides which evidence is seen, how scores combine, and where the line falls is deterministic code.

Within discovery specifically

Discovery is often assumed to be "the AI bit", so it is worth being precise about how much of it is not:

12Defences

Guarding against the model

Hallucination in this system has a specific and serious shape. It is not a wrong fact in a chat reply — it is a confident sentence that eliminates a team. These are the layers that exist between a model's output and that outcome.

Deterministic evidence selection

packages/scoring/src/relevance.ts

The model never chooses the source it is judged against. A model that picked its own evidence could pick evidence supporting the score it already prefers, and two runs would not be comparable.

Temperature zero

llm_call_config.temperature

Every judging and extraction call runs at 0.00. The one exception is criteria drafting at 0.20, where variety helps and a human reviews the output anyway.

Schema before storage

llmGateway · Zod

Output is parsed and validated before anything downstream sees it. An unparseable or mis-shaped response is a failure, not a value — downstream code would otherwise treat fabricated shape as real.

Classified retry

retryStrategy.ts

Each failure class gets a distinct plan, never a blind repeat: too-short halves the context, bad structure adds a format reinforcement, a timeout doubles the limit and prefers a faster model, empty content switches model.

Citations are mandatory

scoreSchemas · discoverySchemas

Every score and every finding must carry a path and a line range. A finding nobody can locate cannot be disputed, and an undisputable finding is worse than a missing one.

Excluded, never zeroed

packages/scoring/src/aggregate.ts

The structural defence against silence becoming a verdict. An unassessed criterion leaves the denominator and marks its dimension PARTIAL; it does not become a zero that looks like every other zero.

Empty is declared, not inferred

discoveryConcerns.ts

Each concern states whether zero is a possible answer. An application can integrate with nothing; it cannot store nothing. A zero where zero is implausible is recorded as unreadable, not as a fact about the team.

Concern, not severity

discoverySchemas.ts

Security findings have no severity field at all — the vocabulary itself is the guard. Severity is a property of a confirmed vulnerability, and with no CVE database and a budgeted file selection, nothing here is confirmed.

The benign explanation is mandatory

discoverySchemas.ts

Every security observation must say what would rule it out, shown next to it. An observation without one reads as an accusation — and accusing a team of a flaw they do not have is the worst outcome available.

Silence is not a conflict

migration 053

A documentation claim only conflicts when the findings actively contradict it — never when they are merely silent. Absence of evidence fails the test explicitly, because the scan read only part of the repository.

Prompt injection handling

promptRenderer.ts · P8.4

Submission source is fenced with a per-call nonce, structurally neutralised, scanned for injection patterns, and never placed in the system prompt. Anything addressed to the model is reported as injection_noted on the score.

Scored twice, compared

varianceService.ts

Two independent runs. Not averaged — averaging hides the disagreement. A submission the system cannot place consistently is one a person should look at, and the flags say which kind of inconsistency it is.

Calibrated against people

E11 golden set

Machine ranking is compared against independent hand rankings, with the pass criteria fixed before the report exists. Failure routes to human judging, not to a lowered bar.

A person decides at the line

flag & decision CHECK constraints

Everything in the cut band is reviewed by a human, and both dismissing a caveat and recording a decision require a written reason — enforced by the database, so the two cannot come apart.

Prompts are versioned and hashed

llm_prompt_template

Content-addressed, one active version per role. A score records which version it ran under, so changing a prompt cannot retroactively re-explain a score already taken.

No ad-hoc prompts exist

CI gate · guard:llm

Every model call has a registered key with declared inputs, its own config and its own metrics. There is no endpoint that takes a prompt, and the build fails if a code path reaches a provider directly.

The one that is missing

There is a gap in this list, and it is the most important one: nothing verifies that a cited file and line actually exist, or that the quoted excerpt matches the source. A model could cite src/foo.ts:42–50 with an invented excerpt and the system would store, display and defend it. Every claim above about citations being checkable currently depends on a reviewer doing the checking by hand. This is item G1 in the companion gap register, and a deterministic fix is available.

13Operations

Running a cohort

On the night, a batch run takes a whole cohort through scan → probe → score. Four decisions shape how it behaves, and each exists because of how an unattended overnight run actually fails.

  • Stage by stage, not submission by submission. All fifty are scanned, then all fifty probed, then all fifty scored. Each stage is bound by something different — disk, containers, a provider — so each has its own concurrency limit, and interleaving would make those limits meaningless.
  • A failure is data, not an exception. Per-submission failures are recorded against the ledger and the run carries on; the summary lists them all.
  • Budget exhaustion pauses, it does not fail. The work already done is worth keeping, and an operator who raises the ceiling should resume rather than restart. Resume and force are separate actions so redoing completed work cannot happen by accident.
  • Progress is written down, not only published. A websocket message is gone on reload — which is exactly when somebody checks on an overnight run.

Discovery is not in this

The batch stages are scan, probe and score. Discovery must be triggered by hand, per submission. Since discovery feeds the principles and standards evaluators, a cohort where some submissions were discovered and others were not is scored on unequal evidence — and nothing currently records which is which.
