Gap register

What Crucible cannot yet do

Seventeen items, found by reading the implementation against its own stated commitments and verified against live source or the running system. All seventeen are now closed by the seven remediation epics E13 – E19. One item remains open, and it is a decision rather than a defect, and it has since been taken: G18 is closed by decision, recorded in ADR 0004.

Nothing here has been deleted. A struck-through entry says somebody fixed this, which has to stay distinguishable from this was never here — the same rule the product keeps for dismissed flags and resolved provenance. Each closed item names the epic that closed it; the build log records what broke during the work.

How to read the severities

Critical means the system could produce a wrong outcome and defend it. High means a real risk to fairness or to the night running at all. Medium means friction or a capability that exists in the API but not where anyone can reach it. Low is polish and configuration.

G1

Cited evidence is never verified against the scanned source

Evidence integrity Closed — E13
What is true today

Every score and every discovery finding carries a path, a line range and an excerpt. The schema enforces that those fields are present and well-formed. Nothing checks that they are real. A search of the scoring and LLM modules finds no code that opens the scanned file, confirms the path exists, checks the line range is within bounds, or compares the quoted excerpt against the source.

Why it matters
A model can cite src/auth/session.ts:42–58 with a plausible, invented excerpt, and Crucible will store it, render it in the reviewer's page, and reproduce it verbatim in the team's appeal packet. The system's entire defensibility argument — "a disputed judgement can be checked rather than debated" — rests on a reviewer manually opening the file. In the cut band, under time pressure, nobody will. This is the one failure mode where Crucible would be confidently, unfalsifiably wrong.
The fix is deterministic and cheap

The scan is already persisted in full. After schema validation and before storage: confirm the path is in the scan; confirm the line range is within that file's length; confirm a normalised form of the excerpt appears at or near those lines. Three outcomes — verified, unverifiable (the file was outside the scan budget, which is honest and should be labelled), or contradicted.

A contradicted citation should not be silently dropped. It is a signal about that response, and the honest handling is to treat the score as SCORING_FAILED and retry — the retry ladder already exists and already has a classification for exactly this shape of problem.

Verified
No verification code exists in scoring, llm or discovery modules

G2

Runs record a pin that is never honoured, and that omits everything which decides the outcome

Run comparability Closed — E14
What is true today

run.pinned_config exists, and its comment states the commitment directly: “P4.4: the model is pinned per run; a config change must not affect an in-flight run.” The batch orchestrator populates it. Two things are wrong with that.

It pins the wrong things. The snapshot holds concurrency limits, batch.cost_ceiling_usd, batch.projection_after and llm.concurrency. It contains no feature flags at all — including feature.discovery.enabled — and none of the parameters that determine an outcome: context budgets, the cut line, the cut band, the variance threshold, minimum cohort size, or which model each call key uses.

And it is written but never read. No code reads pinnedConfig back. The scoring path calls getNumber(...) live, so a configuration change does affect an in-flight run — exactly what the column was created to prevent. The pin is a record of intent, not a mechanism.

score_run — the row the variance comparison actually joins on — pins rubric_versions and a single model string. Both correct, and both far narrower than what shapes a composite.

Why it matters
The whole value of scoring twice is that the two runs are comparable. Change the cut line, a context budget, or the discovery flag between run 1 and run 2, and the variance flags measure a configuration change while reading as model instability. The calibration gate has the same exposure: a gate passed under one configuration silently vouches for a run under another. And because the pin is not enforced, a change made during an overnight run reshapes the second half of it with nothing recording that the halves are not alike.
Shape of the fix

Three parts, and the second is the one that matters:

  • Widen the snapshot to every flag and every outcome-determining setting, derived from the config declaration rather than hand-listed — a hand-listed set silently stops covering settings added later.
  • Honour it. Resolve configuration through the run's snapshot for the life of the run, the way the correlation id is already carried ambiently, so that “pinned” is enforced rather than asserted.
  • Report drift when two compared runs were not executed alike, beside the variance flags and beside the gate verdict.
Verified
pinned_config is written in batchOrchestrator and read nowhere; the snapshot lists four keys and no flags
G3

Discovery is outside the batch, so a cohort is scored on unequal evidence

Discovery Closed — E15
What is true today
The batch stages are scan, probe, score. Discovery appears nowhere in the orchestrator. It is triggered one submission at a time through an organiser-only endpoint.
Why it matters
Discovery feeds the principles and standards evaluators. A fifty-team cohort therefore needs fifty manual triggers, and any that are missed produce submissions scored with less context than their competitors — on the same rubric, in the same ranking, with nothing on screen saying so. The per-submission guard works correctly (an undiscovered submission gets an explicit "none was run" rather than a blank), but there is no cohort-level guard and no report of coverage.
Shape of the fix
Two parts, and the second matters more than the first. Add discovery as an optional batch stage with its own concurrency limit and its own cost ceiling. Then report discovery coverage per cohort and refuse — or loudly warn — when a ranking is computed over a partially discovered field.
Verified
batchOrchestrator contains no reference to discovery
G4

There is no team entity — a team is a string on a submission

Team identity Closed — E17
What is true today
No team table exists. Team identity is team_name TEXT on the submission, with a uniqueness index on (lower(team_name), challenge_id) among current submissions. There is no registration step, no roster, and no assignment of teams to challenges — a team joins by submitting.
Why it matters

Identity by case-normalised string has consequences that only appear under pressure:

  • "Night Shift" and "The Night Shift" are two different teams, and neither knows it.
  • A team that renames between versions creates a second lineage rather than a new version of the first.
  • A team entering two challenges cannot be recognised as the same team.
  • Tokens are labelled with a team name that is never reconciled against the name typed into the form, so the audit trail cannot answer "did this team submit with their own token?"
Shape of the fix
This is a deliberate simplification for a one-evening event, and it may be the right call. The proportionate step is not a full roster: bind the submission token to a team record and take the team's identity from the token rather than from typed text. That closes the reconciliation gap and the rename problem together, and the token already exists.
Verified
No CREATE TABLE for team in any migration; identity is the text column
G5

Discovery is absent from every surface where decisions are actually made

Discovery Closed — E16
What is true today
Discovery is reachable from one place: a link on the individual team review page. It does not appear in the appeal packet, the readiness report, the ranked field, or the submission score page.
Why it matters
The appeal packet is the strongest commitment the system makes — a self-contained document answering "why did we not present?" without system access. If discovery informed the principles and standards scores, then the packet omits part of the basis for the scores it reports. A team disputing a principles score cannot see the map the evaluator was given. That is a governance gap, not a UI one.
Shape of the fix
Add the discovery digest to the appeal packet wherever one informed the run, labelled as context rather than as evidence. Add discovery coverage to the readiness report as an eighth check. Both are additive.
Verified
appealPacket imports no discovery module; readinessReport has no discovery check

G6

reviewer_model is named for a review pass that does not exist

LLM gateway Closed — E14
What is true today
llm.reviewer_model is configured as claude-opus-5 and every call config carries a reviewer_model column. Its only use in the codebase is as the fallback model when the retry ladder decides to switch models. There is no critic pass, no second-opinion pass, and no adversarial check anywhere in the system.
Why it matters
The name implies a control that is not there. Anyone auditing this system — including a future maintainer — would reasonably read the schema and conclude that scores are reviewed by a stronger model. They are not.
Shape of the fix
Cheapest honest fix: rename it fallback_model, which is what it is. The larger question — whether a genuine adversarial review pass on cut-band scores would be worth its cost — is a real design decision, and the current naming obscures that it has not been made.
Verified
Sole use: if (switchModel && resolved.config.reviewerModel) return ...
G7

Discovery runs synchronously inside one HTTP request

Discovery Closed — E15
What is true today
Seven sequential model calls, each with a 180-second timeout, inside a single request. The worst case is over twenty minutes on one connection. There is no job record, no progress, no resumability, and a dropped connection loses the visibility even though the work continues.
Why it matters
The platform request timeout is 30 seconds. Any proxy or load balancer in front of the API will sever the connection long before discovery finishes. The run itself completes and persists — so the data is safe — but the operator sees a failure and has no way to tell a hung run from a finished one.
Shape of the fix
The run ledger and the websocket progress hub both already exist and are used by the batch orchestrator. Open a ledger run, return immediately, publish per-concern progress, exactly as batch does. This is the pattern the reference implementation reached for as well, with a durable queue behind it.
G8

Re-running discovery cannot say what changed

Discovery Closed — E16
What is true today
A second discovery supersedes the first wholesale. The superseded run keeps its findings — correctly, as evidence — but nothing reconciles the two sets.
Why it matters
For a one-evening hackathon this is nearly harmless: a submission is discovered once. It matters the moment Crucible is used across rounds, or for a team that resubmits after fixing a security observation — the reviewer cannot see that the observation is gone, only that the new run does not list it, which is a different and weaker statement.
Shape of the fix
The reference implementation classifies each incoming finding as NEW/UPDATE/DUPLICATE against stored state. A cheaper deterministic version is available here: match on (kind, label, path) and report added, unchanged and disappeared. No model call needed.
G9

Criteria cannot be edited in the application

Missing interfaces Closed — E18
What is true today
The API supports creating, patching and deleting criteria, and the web client exports editCriterion. No component calls it. CriterionCard is read-only.
Why it matters
The quality gate flags criteria as NEEDS_REWRITE — deliberately, rather than dropping them — and shows the reviewer exactly why. And then offers no way to rewrite them. A committee can re-weight but cannot reword an anchor, fix an evidence specification, or resolve a flagged criterion without falling back to the API.
Shape of the fix
An editable CriterionCard on a draft rubric, with the same anchor-distinctness and evidence-specification checks the principles authoring form already applies.
Verified
editCriterion is exported and has no callers in the UI
G10

The calibration workflow has no interface — only its verdict does

Missing interfaces Closed — E18
What is true today
The web reads the gate verdict and displays it. Building a golden set, recording the two independent hand rankings, running the calibration report and recording the go/no-go decision are all API-only.
Why it matters
This is the most consequential decision in the system — whether it is fit to eliminate anyone — and it is the least accessible. A gate that can only be exercised through curl is a gate that gets skipped when the evening is tight, and skipping it is exactly what the design was built to prevent.
Shape of the fix
A calibration page: assemble the golden set, capture each ranker's order separately, run the report, and record the decision with its rationale. The ordering constraint — hand rankings before machine scoring — should be enforced by the UI, not just documented.
G11

Discovery spend is outside every cost ceiling

Discovery Closed — E15
What is true today
Cost accrues per call and is attributed to the submission, correctly. But the batch ceiling ($250) only applies to a batch run, and discovery is not in the batch. The per-run ceiling ($50) applies to a ledger run, and manual discovery opens none.
Why it matters
Seven calls per submission across fifty teams is unbudgeted and unbounded. Nothing stops it, and nothing warns before it happens.
Shape of the fix
Falls out of G3 for free: putting discovery in the batch puts it under the batch ceiling. Failing that, a discovery.cost_ceiling_usd and a projection before a bulk trigger.
G12

A reviewer cannot dismiss or annotate a discovery finding

Discovery Closed — E16
What is true today
Every security observation ships with a benign_explanation naming what a reviewer should check to rule it out. When the reviewer checks it and it is benign, there is nowhere to record that.
Why it matters
The observation stays on the page, the tile stays amber, and the next reviewer repeats the work. Worse, a resolved observation and an unexamined one look identical — which is the same category of confusion the tile design works hard to avoid elsewhere.
Shape of the fix
The review module's flag-dismissal pattern applies directly, including its CHECK constraint tying a dismissal to its reason. Dismissal should supersede rather than delete, for the same reason discovery runs do.

G18

The Worker / Reviewer / Judge pattern is not applied to the calls that decide scores

LLM gateway Closed by decision — ADR 0004
What is true today

P4.3 requires a Worker / Reviewer / Judge sequence for artifacts classified CRITICAL. Rubric synthesis has one. The four call keys that actually produce scores — scoring.criterion, scoring.engineering, scoring.principles and scoring.standards — do not. They are single-pass calls with schema, content and semantic validation, retry on failure, and since E13 a citation check against the scanned source. What they do not have is a second model reading the first model's judgement.

G6 closed the part of this that was a naming problem: reviewer_model was renamed to fallback_model, because a column named for a pass that does not run is worse than an absent column. This is what remained once the name told the truth.

Why it is not simply implemented

Scoring is the dominant spend in an evaluation. Adding a reviewer and a judge to the four keys above roughly triples it, and the benefit is unmeasured: the calibration gate exists precisely to find out whether this system's judgement tracks a committee's, and it has not been run against a golden set yet.

Implementing it first would spend the budget on an assumption. Running calibration first produces the evidence that says whether it is needed, where, and how much it moves the ranking.

The decision taken

Of the three defensible options — apply the pattern to all four keys, apply it only where calibration shows material disagreement, or record the departure as a reasoned exception — the third was chosen.

P4.3 is amended rather than quietly departed from. The principle now scopes itself to llm_call_registry.requires_review, which is the single place the rule is declared, and states plainly that criticality is not a synonym for reviewed: it governs retry policy, terminality and logging. The controls standing in the pattern's place are named there and in the ADR — citation verification against the scan, three validations, deterministic evidence selection, temperature 0 under a per-run config pin, the double score run, the calibration gate, and human review of every placement in the cut band.

It is pinned by a test, not only by prose. The exact set of reviewed keys and the reason each CRITICAL key is exempt are asserted in reviewRequirement.test.ts, so a CRITICAL call key added later without a review pass appears in neither list and fails by name. That is the same mechanism the P8.1 allow-list uses, for the same reason.

The decision is cheaply reversible: adding review is a registration, a stored prompt and a flag, and the machinery is already in use for rubric synthesis. What would reverse it is calibration showing material disagreement concentrated in one key — and it would justify the cost for that key, not for all four.

What the reference implementation has that this does not

Crucible's discovery was modelled on a much larger upstream capability — roughly 8,200 lines across nine services. Several omissions were deliberate and are recorded as such in ADR 0003. These are the ones that were not deliberate.

If only three things are done

Written when all seventeen were open, and kept as written. All three were done, in this order, for these reasons:

#ItemBecause
1 G1 — verify citations against the scan It is the only item that can make the system confidently wrong in a way nobody catches. Everything else is visible when it goes wrong.
2 G2 — pin what decides the outcome, and honour the pin The pin is recorded but not enforced, and omits every setting that shapes a composite. The double-run comparison and the calibration gate — the two mechanisms that establish fitness — can both be quietly invalid.
3 G3 — discovery in the batch, with coverage reported Closes G11 for free, and removes the fairness risk of ranking a partially discovered field.

Compiled by reading the Crucible source at the state verified by pnpm verify — 1,675 tests across 95 files, plus 119 end-to-end journeys, all passing. Every item was checked against live source, the live configuration tables, or the running development instance. Where an item says verified, that is the specific check performed.
